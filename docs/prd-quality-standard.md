# Lincoln PRD 内容质量标准（core-v2）

## 1. 目的与适用边界

优秀 PRD 不是“章节齐全的文档”，而是团队能够据此做出一致决策、实现正确行为、验证业务结果的需求基线。它应同时回答：为什么值得做、为谁做、做成什么、不做什么、如何验收、如何发布，以及出现分歧由谁裁决。

core-v2 适用于新 PRD。Markdown 是叙事事实源；结构化 YAML 只保存追溯和评审，不替代业务说明。本文定义内容下限与人工评审方法，不承诺用规则替代产品判断，也不要求轻量需求堆砌无关材料。

## 2. 谁使用 PRD，分别做什么决策

| 读者 | 需要回答的问题 | 使用结果 |
|---|---|---|
| 业务负责人/决策人 | 问题是否真实，价值和优先级是否成立，边界是否符合策略 | 批准方向、资源和关键取舍 |
| PM | 证据是否充分，范围是否闭环，规则是否一致，版本变化影响什么 | 维护需求基线并协调决策 |
| 设计 | 用户、场景、流程、异常和体验判据是否清楚 | 覆盖正确状态的原型与体验方案 |
| 研发 | 行为、边界、依赖、权限和非功能要求是否可实现、可估时 | 技术方案、工作量与发布可行性判断 |
| QA | 每条需求是否有可观察、可执行、可追溯的验收条件 | 测试场景、回归范围与质量结论 |
| 运营/客服/数据 | 上线条件、指标口径、培训和回滚是否明确 | 运营准备与上线后效果跟踪 |
| 安全/法务/合规 | 数据、权限、审计和残留风险是否可接受 | 守门意见或发布限制 |

“PM 已批准”不能代替跨职能认可。最终交付基线需要 PM、设计、研发、QA 对同一 PRD 版本分别评审；批准记录由后续集成机制写入 `{process_slug}/pages/docs/prd-review.yaml`，不得由生成 prompt 自动伪造。

## 3. 分角色责任与 PM 全周期工作

### 3.1 责任分工

| 角色 | 必须负责 | 不应外包给其他角色 |
|---|---|---|
| PM | 问题证据、价值、范围、业务规则、优先级、指标和开放问题裁决 | 对需求正确性和跨章节一致性负责 |
| 设计 | 用户路径、交互状态、异常体验、可访问性、原型覆盖 | 指出无法表达或体验断裂的需求 |
| 研发 | 依赖、数据与权限约束、非功能可达性、发布/回滚可行性 | 指出实现歧义、矛盾与不可验证承诺 |
| QA | 验收可执行性、正反例、边界覆盖、需求到测试的追溯 | 指出“能开发但无法证明完成”的条目 |
| 决策人/守门人 | 有权范围内的范围、风险、合规和发布取舍 | 在 gate 前裁决关键开放问题 |

### 3.2 PM 前期：建立证据，而非先填模板

1. 明确业务背景、目标用户、问题频率和当前替代方案。
2. 用访谈、日志、工单、数据或既有研究支撑问题；记录来源、样本与时间范围。
3. 识别受益者、成本承担者、运营者、决策人和否决者，处理目标冲突。
4. 获取现状基线，与决策人约定目标值、时间窗和指标口径。
5. 先确认方向与非目标，再展开功能；禁止把未决关键问题藏进文档。

### 3.3 PM 中期：把方向变成可执行行为

1. 将需求拆成用户可观察行为，为每条核心需求分配稳定 `REQ-NNN`。
2. 与设计走查主流程、空态、异常、权限和状态变化；与研发确认依赖及非功能约束。
3. 与 QA 用具体正例、反例和边界例写 Given/When/Then，为每条验收分配 `AC-NNN` 并引用需求 ID。
4. 检查执行摘要、范围、流程、验收、原型和发布条件是否讲同一件事。
5. 运行确定性校验，再组织人工评审；CLI 通过不等于业务正确或团队批准。

### 3.4 PM 后期：维护同版本基线与结果闭环

1. 将评审意见结构化闭环，版本变化后同步更新快照、追溯和评审。
2. 原型与测试发现的缺口回到 PRD 裁决，不允许只改页面或测试而保留错误需求。
3. 发布前核对依赖、灰度条件、运营准备、监控和回滚。
4. 在约定时间窗复盘指标；未达目标时记录新证据和下一步决策，而非修改历史基线冒充成功。

## 4. core-v2 的 15 个核心章节

新文档在顶部同时包含：

```markdown
<!-- prd-contract: core-v2 -->
<!-- version: v1.0 -->
```

15 章使用下表中的 H2 名称并保持顺序；数字前缀可选。额外业务附录可放在核心章节之后。每章必须回答对应问题，空标题、空表格、纯占位语和复制模板均不合格。

| # | H2 章节 | 必须回答的业务问题 | 最低内容证据 |
|---|---|---|---|
| 1 | 版本说明 | 这是哪一版，谁决策，给谁看，何时发布 | 版本、状态、决策人、目标时间、读者 |
| 2 | 修订记录 | 为什么变化，变化前后如何区分 | 版本、日期、作者、变更摘要 |
| 3 | 执行摘要 | 为谁解决什么，方案和价值是什么 | 用户、问题、首版方案、业务结果的短摘要 |
| 4 | 问题与证据 | 问题有多真实、多频繁、多严重 | 带来源/样本/时间的事实、现状基线；假设单列 |
| 5 | 用户与相关者 | 谁使用、谁受益、谁运营、谁能阻止 | 角色任务、利益、权力、冲突与责任 |
| 6 | 目标与成功指标 | 何时、用什么口径证明有价值 | 每项含指标、基线、目标值、时间窗、口径/来源 |
| 7 | 范围与非目标 | 首版做什么，明确不做什么 | 范围与独立“非目标”小节；关键排除项及理由 |
| 8 | 用户故事 | 谁在什么场景完成什么任务、获得什么收益 | 分角色故事，可追溯到需求 |
| 9 | 功能需求 | 系统必须表现什么用户可观察行为 | 唯一 `REQ-NNN`、行为、优先级、业务结果 |
| 10 | 业务流程与规则 | 正常、分支、异常、权限和状态如何处理 | 触发、步骤、业务规则、失败行为；图示不能替代关键文字 |
| 11 | 验收标准 | 用什么具体例子证明需求完成 | 唯一 `AC-NNN`、同行 `REQ-NNN`、Given/When/Then |
| 12 | 非功能需求 | 性能、安全、体验等达到什么阈值 | 可测阈值、统计口径、适用条件 |
| 13 | 依赖与发布 | 依赖谁，如何灰度、全量和回滚 | 依赖就绪时间、发布门槛、迁移/运营/回滚安排 |
| 14 | 风险与开放问题 | 哪些风险由谁处理，哪些决策已发生 | 风险责任人、缓解动作、关键决策；无隐藏占位 |
| 15 | 相关产物链接 | 证据、追溯、评审、原型和测试在哪里 | 使用稳定相对路径，不复制多份事实 |

### 4.1 指标契约

至少提供一张成功指标表，每条指标都必须同时具有具体基线、目标值和时间窗。基线写明来源与统计时点，目标值可比较，时间窗可判断何时复盘，口径说明分子/分母或起止事件。

```markdown
| 指标 | 基线 | 目标值 | 时间窗 | 口径/来源 |
|---|---|---|---|---|
| 搜索成功率 | 72%（2026-10 日志） | ≥90% | 上线后 8 周 | 首次搜索后打开有效引用的会话占比 |
```

“显著提升”“尽快达到行业领先”不是可验收目标。尚无基线时，PM 应先完成测量或明确基线采集决策，不能用空值绕过。

### 4.2 ID 与内容追溯契约

- 需求 ID 使用 `REQ-` 加至少三位数字，如 `REQ-001`；验收 ID 同理，如 `AC-001`。
- ID 在定义章节唯一、大小写固定，修订时稳定；删除后不复用。
- 每条验收在同一行/条目中引用一个已定义需求 ID；每条核心需求至少有一条验收。
- Markdown 中的 ID 与 `{process_slug}/pages/docs/prd-traceability.yaml` 保持一致。该 sidecar 后续继续关联来源、故事、流程、原型页面和测试场景，本标准不复制其实现。
- 分角色评审固定写入 `{process_slug}/pages/docs/prd-review.yaml`。PRD 版本变化后，旧版本评审不能冒充当前批准。

## 5. 团队评审 rubric

每个维度按 0–2 分评审：

- **0 分**：缺失、纯占位、互相矛盾或无法执行。
- **1 分**：有内容但证据、边界、口径或责任不完整，需要返工。
- **2 分**：具体、一致、可验证，目标读者能据此独立工作。

| 维度 | 2 分判据 | 主要评审者 |
|---|---|---|
| 问题与证据 | 问题重要且来源可核，事实与假设分开 | 业务负责人、PM |
| 用户与相关者 | 任务、利益、权力和冲突明确 | PM、设计、运营 |
| 目标与指标 | 基线、目标、时间窗和口径完整，能归因复盘 | 业务负责人、PM、数据 |
| 范围与非目标 | 首版边界清楚，无隐含的“顺便一起做” | 全角色 |
| 行为与规则 | 正常、异常、权限和状态闭环，无跨章矛盾 | 设计、研发、QA |
| 验收与追溯 | 每条核心需求有可执行验收，ID 和关系完整 | QA、研发、PM |
| 非功能与发布 | 阈值可测，依赖、灰度、监控、回滚可执行 | 研发、QA、运营、守门人 |
| 治理与可读性 | 版本、决策、风险、链接一致，无重复事实源 | 全角色 |

建议基线：没有 0 分，总分至少 14/16，且 PM、设计、研发、QA 对同版本无未闭环的 `changes_requested`。任何越权风险、关键开放问题、缺失验收或缺失发布回滚均为阻断项，不能被其他高分抵消。

## 6. 裁剪原则：减少材料，不删除答案

1. **按风险加深，而非按模板加重**：低风险文案调整可简化证据和流程；权限、资金、合规、数据迁移等高风险需求必须展开。
2. **15 个核心问题仍要回答**：不适用时写“不适用”的具体决策和理由，不能留空或只写 N/A。
3. **合并表达，不制造重复事实**：短需求可用一张表表达多个条目，但保持章节入口和单一事实源。
4. **轻量工作流显式声明裁剪**：由集成工作流记录裁剪模式，区分有意裁剪与意外漂移；不得删除 core-v2 标记来逃避检查。
5. **证据可链接**：已有研究、架构或测试资产直接链接，不在 PRD 复制技术设计或整段原始访谈。
6. **裁剪不等于跳票**：任何裁剪都不能移除关键业务决策、非目标、需求—验收追溯或必要守门人意见。

## 7. 确定性质量校验

```bash
# 自动识别：只有显式 core-v2 标记才启用语义质量检查
python3 scripts/lincoln_prd_quality.py path/to/prd.md

# 新 PRD 在 clarify 阶段显式检查
python3 scripts/lincoln_prd_quality.py {process_slug}/pages/docs/prd.md --mode core-v2

# 渲染后的 HTML 使用同一 Markdown 事实源
python3 scripts/lincoln_prd_quality.py {process_slug}/pages/docs/prd.html --json
```

检查范围：15 章及顺序、章节非空且非占位、版本和 core-v2 标记、指标字段和值、显式非目标、REQ/AC 格式与唯一性、验收引用及需求验收覆盖。错误包含章节、错误码和修复动作。

退出码：`0` 通过；`1` 内容质量失败；`2` 文件不存在、读取失败或 CLI 使用错误。校验器只使用 Python 标准库，不调用 LLM，结果可重复。

它无法判断证据是否真实、方案是否最优或团队是否认可，因此不能替代上述 rubric 和 Human Gate。

## 8. Legacy 兼容

没有 core-v2 标记的旧文档继续使用 issue-129 的 13 章结构检查：版本说明、修订记录、功能列表、需求背景、用户故事、功能拆解、业务流程图、验收标准、业务规则、非功能需求、关联系统/接口、相关产物链接、风险与开放问题。

legacy 模式只检查既有 H2 结构，不把新的指标、ID 或非空语义追溯强加给旧文档；缺失旧章节仍失败。新 PRD 不得通过省略或删除标记进入 legacy。升级旧文档时应一次补齐 core-v2 内容，而不是仅添加标记。

## 9. 可测试样例

`tests/fixtures/prd-quality/` 提供完整金标准、legacy 13 章样例及空章节、纯占位、缺指标、缺追溯、非法需求 ID、重复验收 ID 反例。`tests/test_lincoln_prd_quality.py` 同时覆盖 Markdown、渲染 HTML、CLI 错误和 prompt 契约，全部确定且不依赖 LLM。
